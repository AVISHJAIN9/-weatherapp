# 14.6 Caching Strategies & Multi-Tier Invalidation

This chapter analyzes multi-tier caching architectures designed to shield downstream databases and disks from high-read contest traffic.

---

## 1. What It Is in Plain Words
Caching stores copies of frequently accessed data in high-speed, volatile memory (such as RAM) so that future requests can be served in sub-milliseconds rather than recalculating or fetching from slower storage layers.

---

## 3. Caching Strategy Comparisons

| Pattern | Write Path | Read Path | Data Freshness | Complexity | Ideal Use Case in Judge |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Cache-Aside (Selected)** | Application writes to DB, invalidates cache | App checks cache; on miss, reads DB & populates cache | Eventual consistency | Low | **Problem Statements & User Profiles** |
| **Read-Through** | Cache library manages DB writes | App queries cache only; cache fetches from DB on miss | Consistent | Moderate | Service-level abstracted data access |
| **Write-Through** | App writes to cache; cache writes synchronously to DB | App reads from cache | High | Moderate | User session tokens |
| **Write-Back (Write-Behind)** | App writes to cache; cache writes asynchronously to DB | App reads from cache | Risk of data loss on crash | High | Suboptimal for contest submissions |
| **Write-Around** | App writes directly to DB without updating cache | Cache populated on subsequent read miss | Low cache pollution | Low | Submission log archives |

## 4. Cache Eviction Policies & Invalidation Patterns
- **Eviction Policy**: Redis configured with `volatile-lru` (Least Recently Used among keys with an explicit TTL) and `allkeys-lru` for leaderboard read caches.
- **Cache Stampede / Thundering Herd Prevention**:
  When a hot key expires (e.g., the contest leaderboard during final minutes), thousands of concurrent requests can simultaneously query the database. We mitigate this using:
  1. **Probabilistic Early Expiration (XFetch Algorithm)**: Recomputes the cache slightly before true TTL expiration based on access probability.
  2. **Distributed Mutual Exclusion (Mutex Lock)**: First thread acquires a Redis lock to recompute the leaderboard; subsequent requests serve slightly stale cache or wait.

---

## 5. What Breaks First Across Scaling Orders
- **$10\times$ Load**: Leaderboard cache TTL set too short (e.g., 0.1s), causing high Redis CPU utilization.
- **$100\times$ Load**: Test case files filling worker `/dev/shm` RAM disks if multiple concurrent problems run simultaneously. **Fix**: Implement LRU eviction on node `/dev/shm` test case directories.
- **$1,000\times$ Load**: Network interface saturation on Redis master from serving high-volume leaderboard payloads. **Fix**: Compress JSON payloads using gzip/snappy and fan out across Redis read replicas.

## 6. 30-Second Interview Answer
> "We implement a five-tier caching hierarchy: Cloudflare CDN handles static problem descriptions at the edge; Redis acts as a distributed cache-aside layer for user profiles and problem metadata; and sorted sets cache the live contest leaderboard. At the worker level, test case files are downloaded once from S3 and cached directly in local memory-backed RAM disks (/dev/shm), allowing execution sandboxes to feed test data into Python processes with zero disk I/O latency."
